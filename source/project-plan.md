# خطة مشروع المنيو الإلكتروني

الحالة: خطة في انتظار موافقة صريحة من صاحب المشروع وأمر بالبدء. لا تنفيذ أو كتابة كود قبل ذلك. المعمارية المجانية تحتاج اختبارًا فعليًا بالحسابات قبل اعتماد عرض وسائط Drive في الإنتاج.

تاريخ الإعداد: 8 أكتوبر 2026.

## الهدف والنطاق المؤكد

موقع يعرض منتجات المحل وأسعار القطعة والكرتونة عند وجودها، مع لوحة إدارة محمية لإدارة بيانات المحل والمنتجات والعروض. واجهة العميل مناسبة للموبايل وتحتوي على شاشة بداية بشعار المحل وحركات انتقال، وزرين في أسفل الشاشة لواتساب وفيسبوك.

- Firebase Authentication: تسجيل دخول الإدارة.
- Cloud Firestore: البيانات النصية والأسعار والعروض والإعدادات وروابط الملفات ومعرّفاتها.
- Firebase Hosting: استضافة الموقع.
- Google Drive الخاص بصاحب المحل: المصدر الدائم لصور المنتجات والشعار وصور العروض والملفات الكبيرة.
- Firebase Spark: التشغيل دون تفعيل حساب فوترة، داخل حصص الخطة المجانية.
- Google Identity Services: ربط حساب Drive من متصفح الأدمن ورفع الملفات مباشرة إلى Drive.
- لا يعتمد الحل على Firebase Functions أو Firebase Storage أو خادم مدفوع.

النطاق: كتالوج وعروض مع التواصل عبر واتساب وفيسبوك فقط. لا توجد سلة أو طلبات أو دفع داخل الموقع.

مشروع Firebase موجود باسم Menu ومعرّف menu-3ebba. تم التحقق من وجود Firestore بقاعدة (default) وfreeTier=true، وموقع Hosting الافتراضي menu-3ebba.web.app. أكد صاحب المشروع تفعيل Authentication باستخدام Email/Password. تم تسجيل Web app باسم Menu Web ومعرّف 1:982988699945:web:3d3447af4cd1a16dda1f38؛ لا يوجد موقع منشور بواسطة هذا العمل.

تفاصيل متبقية للإعداد: OAuth client، وطريقة تعريف حساب الإدارة. نوصي بإيميل وكلمة مرور لأنهما مدعومان مباشرة في Firebase Auth؛ اسم مستخدم حرفيًا يحتاج قرارًا منفصلًا. أحجام الملفات ستُحدد عمليًا مع إظهار الحجم والتحقق منه قبل الرفع.

لا تُرسل كلمات المرور أو مفاتيح OAuth الخاصة داخل المحادثة. ربط الحساب يتم أثناء إعداد المشروع من خلال مسار آمن.

## قراءة مرجع التصميم

المرجع الذي جرى فتحه وفحصه في المتصفح:

[FRAMES — F1 FRAMES](https://framesmego.myeasyorders.com/collections/F1FRAMES).

الملامح التي نستفيد منها:

- صور كبيرة وواضحة داخل شبكة منتجات.
- حواف دائرية للكروت والصور.
- شارة خصم بارزة، وسعر أصلي وسعر مخفض.
- رأس صفحة واضح ومسار للوصول للأقسام والبحث.
- شريط تنويه أعلى الموقع.

هذا مرجع لتنظيم العرض. هوية المحل والألوان والشعار قابلة للتعديل من الأدمن، مع هوية مؤقتة متناسقة. لا ندخل سلة المرجع أو النشرة البريدية في النطاق.

تمت قراءة مهارتي ui-styling وui-ux-pro-max واستخدام إرشاداتهما للتخطيط. أُجري بحث محلي لنظام التصميم؛ اقتراحاته العامة للشبكات والحركات مفيدة، لكن لوحة ألوانه وخطوطه ليست هوية معتمدة للمشروع. نجهز ثيمًا افتراضيًا مناسبًا للكتالوج وقابلًا للتخصيص، وخطًا يدعم العربية والإنجليزية.

## تجربة العميل المقترحة

1. شاشة بداية قصيرة بشعار المحل، مع مخرج واضح عند تأخر الشبكة. يظهر بديل بسيط لحين تحميل الشعار في أول زيارة. لا يتكرر الانتظار عند كل تنقل.
2. رأس صفحة يعرض الشعار والاسم والبحث.
3. مساحة للعروض الخاصة بصورة وعنوان وتفاصيل وشروط وسعر إن كان العرض يتضمن سعرًا.
4. أقسام المنتجات وفلاتر بسيطة، مع شبكة مناسبة للموبايل والكمبيوتر.
5. كرت المنتج: الصورة والاسم وسعر القطعة وسعر الكرتونة إن وُجد وشارة الخصم وحالة التوفر.
6. صفحة تفاصيل المنتج: الصور والوصف والأسعار ومحتوى الكرتونة والخيارات عند إدخالها، وزر تواصل بخصوص المنتج على واتساب.
7. قسم العروض: المنتجات ذات الخصومات الفعالة، والباقات، والعروض الخاصة.
8. شريط ثابت في الأسفل: واتساب يفتح محادثة الرقم المسجل في الإدارة، وفيسبوك يفتح رابط الصفحة المسجل. نترك مساحة أسفل المحتوى حتى لا يغطيه الشريط.

## تجربة الإدارة المقترحة

- تسجيل دخول واستعادة كلمة المرور وتسجيل خروج، مع رسائل عربية واضحة عند الخطأ.
- إعدادات المحل: الاسم والوصف بالعربية والإنجليزية، والشعار ورقم واتساب ورابط فيسبوك والعملة والألوان واللغة الافتراضية.
- ربط Google Drive: زر ربط، وحالة الاتصال، والمجلد الخاص بالمنيو، واختبار رفع، وخيار إعادة الربط عند سحب الإذن.
- إدارة الأقسام وترتيب عرضها.
- إضافة وتعديل وإخفاء المنتجات، ومعاينة النتيجة قبل النشر.
- إدارة خصومات المنتجات والباقات والعروض الخاصة.
- مكتبة وسائط تعرض الصور والملفات والفيديوهات التابعة للتطبيق، وتوضح استخدامها وحالة إتاحتها عبر Drive.
- واجهة الإدارة تعمل على الموبايل؛ نستخدم حقولًا مجمعة وخيارات تظهر عند الحاجة بدل نموذج طويل مزدحم.

### دليل تفعيل Google Drive داخل الإدارة

طلب صاحب المشروع أن يعرف مستخدم لوحة الإدارة كيف يجهز Google Drive API. نضيف شاشة إعداد عربية وإنجليزية بها خطوات وروابط مباشرة وحالة تقدم:

1. اختيار مشروع Google Cloud المرتبط بـFirebase؛ لهذه النسخة هو menu-3ebba.
2. فتح صفحة Google Drive API في Google Cloud Console والضغط على Enable.
3. إعداد Google Auth Platform / OAuth consent screen: اسم التطبيق وبيانات الاتصال والجمهور، وحساب الأدمن كمستخدم اختبار أثناء الإعداد.
4. تحديد صلاحية drive.file للملفات التي ينشئها التطبيق أو يختارها المستخدم له، دون طلب الوصول إلى Drive كله.
5. إنشاء OAuth Client من نوع Web application، وإضافة رابط الموقع إلى Authorized JavaScript origins؛ لا نطلب Client Secret أو Service Account key داخل الإدارة.
6. نسخ Client ID في حقل الإعدادات. عند الحاجة للعرض العام، نشرح إنشاء API key مقيد بـDrive API وروابط الموقع، مع اختبار دعمه لعرض الصور قبل اعتماد المسار.
7. الضغط على «ربط حساب Google»، ثم إنشاء مجلد المنيو الخاص بالتطبيق، واختبار رفع صورة وعرضها للزائر.
8. توضيح حالات الإعداد الناقص، وإلغاء الإذن، وانتهاء جلسة الرفع، ومنع المشاركة العامة بواسطة سياسات حساب Google Workspace، مع خطوة إصلاح مناسبة لكل حالة.

الواجهة ترشد المستخدم، ولا تدعي أنها تستطيع تفعيل Drive API أو إنشاء OAuth client تلقائيًا بمجرد إدخال رابط المجلد. نجاح الربط لا يساوي نجاح ظهور الصور للزائر؛ نعرض حالة مستقلة لكل اختبار.

## الأسعار والعروض

### المنتج

- الاسم والوصف بالعربية والإنجليزية، والصور والقسم والتوفر.
- سعر القطعة مطلوب.
- سعر الكرتونة اختياري؛ غيابه يمثل بقيمة فارغة، ويُخفى من واجهة العميل.
- عدد القطع داخل الكرتونة اختياري، ويظهر عند وجوده.
- الأسعار تحفظ بوحدة العملة الصغرى لتجنب أخطاء الكسور العشرية.
- المقاسات والألوان والخيارات اختيارية؛ لا يحتاج المنتج البسيط لإدخالها. ندعم سعرًا مختلفًا للخيار إن أدخله الأدمن.

### الخصم الإضافي

- نوع الخصم وقيمته، ونطاق التطبيق على القطعة أو الكرتونة أو كليهما، وتاريخ البداية والنهاية عند الحاجة.
- السعر النهائي لا يمكن أن يكون سالبًا، والنسبة لا تتجاوز 100%.
- يظهر المنتج تلقائيًا في العروض خلال مدة الخصم الفعال، مع السعر قبل الخصم وبعده.
- إزالة الخصم أو انتهاء مدته تزيل المنتج من عروض الخصم تلقائيًا.
- لا يُطبّق خصم الكرتونة إذا لم يكن لها سعر.

### باقة عدة منتجات

- عنوان وصورة ووصف ومجموعة منتجات وكميات ووحدة بيع لكل عنصر: قطعة أو كرتونة إن كانت متاحة.
- سعر نهائي للباقة، ومدة نشر اختيارية، وشروط العرض.
- سعر الباقة مستقل؛ لا نجمع عليه خصومات عناصرها تلقائيًا، حسب إجابة صاحب المشروع.
- تعديل سعر أحد العناصر أو إخفاؤه يحتاج سلوكًا محددًا: إظهار تنبيه للإدارة ومراجعة الباقة قبل إعادة نشرها.

### عرض خاص

- عنوان ووصف تفصيلي وصورة رئيسية وشروط ومدة العرض.
- منتجات مرتبطة اختيارية، وسعر أو عبارة ترويجية بحسب نوع العرض.
- خيار تمييزه في أعلى الصفحة، وترتيب ظهوره، ومسودة أو منشور.
- العد التنازلي يظهر فقط إذا كان هناك موعد انتهاء حقيقي.
- توقيت الجداول يُعرض حسب Africa/Cairo، ويحفظ في قاعدة البيانات بتوقيت UTC.

## تقسيم التخزين والخدمات

| العنصر | مكانه |
| --- | --- |
| الحساب وكلمة المرور | Firebase Authentication؛ لا نحفظ كلمة المرور في Firestore |
| بيانات المحل والأسعار والأقسام والعروض | Cloud Firestore |
| روابط Drive ومعرّفات الملفات وحجمها ونوعها | Cloud Firestore |
| الصور والشعار والملفات الأصلية والنسخ المضغوطة | Google Drive الخاص بصاحب المحل |
| الواجهة وملفات التطبيق | Firebase Hosting |
| ربط Drive والرفع | متصفح الأدمن باستخدام Google Identity Services وDrive API |
| OAuth access token | ذاكرة جلسة الأدمن فقط؛ لا يحفظ في Firestore أو localStorage |
| OAuth client ID ومفتاح API المقيد إن لزم العرض العام | إعدادات التطبيق العامة؛ معرفات وليست OAuth client secret |

هذا المسار لا يستخدم OAuth client secret أو refresh token ولا يحتاج Secret Manager. عند انتهاء access token، يطلب الأدمن تجديد الاتصال بزر من الواجهة. لا توجد عمليات رفع غير مراقبة بعد إغلاق المتصفح.

ربط Drive يحتاج OAuth؛ كتابة رابط مجلد لا تعطي التطبيق صلاحية رفع الملفات. المقترح استخدام صلاحية drive.file للملفات التي ينشئها التطبيق أو يختارها المستخدم له، مع مجلد ينشئه التطبيق أو يختاره المستخدم عبر Google Picker. الصلاحية لا تعني الوصول تلقائيًا لكل الملفات الموجودة داخل مجلد قديم.

الدخول إلى لوحة الإدارة وربط Drive عمليتان منفصلتان. الاقتراح الأول للدخول هو إيميل وكلمة مرور في Firebase Auth. إذا كان اسم المستخدم حرفيًا شرطًا، نحدد مسار تحويله لحساب Auth بشكل آمن ولا ننشر قائمة حسابات الإدارة للزوار.

## مسار الملفات في النسخة المجانية

### ربط الحساب

1. الأدمن يسجل الدخول، وتتحقق Firestore Rules من حساب الإدارة المسموح له.
2. يضغط ربط Google Drive، ويوافق صاحب الحساب على صلاحية drive.file المطلوبة عبر Google Identity Services.
3. يحصل المتصفح على access token قصير العمر ويحفظه في الذاكرة فقط.
4. التطبيق ينشئ مجلدًا للمنيو داخل Drive الخاص بالحساب، أو يختار المستخدم موردًا يدعمه Google Picker.
5. Firestore يحفظ معرّف المجلد وحالة الاتصال والبيانات غير السرية فقط.

### رفع الصور والملفات

1. اختيار الملف مع معاينة وفحص الحجم والنوع.
2. تجهيز نسخة صورة مناسبة للعرض عند الحاجة، مع بقاء الأصل والنسخة في Drive.
3. رفع قابل للاستكمال على دفعات من المتصفح مباشرة إلى Drive، مع شريط تقدم وإعادة محاولة عند انقطاع الشبكة. لا تمر الملفات عبر Firebase Hosting أو Firestore.
4. اعتماد الملف بعد التأكد من نجاح الرفع وقراءة بياناته من Drive.
5. حفظ driveFileId وdriveUrl وmimeType وsize ومعرّف وسائط داخلي في Firestore.
6. عند فشل حفظ بيانات المنتج، يحتفظ النظام بمسودة أو يسجل الملف غير المرتبط لتنظيف قابل للاسترجاع بدل فقد الملف أو تركه دون تتبع.

نستخدم resumable uploads، ونختبر CORS واستجابة جلسة الرفع وقراءة Range واستئناف الشبكة. جلسة الرفع ذات صلاحية حساسة، فلا توضع في الروابط العامة أو سجل المحادثة، ولا نخزن رموز Google في بيانات المنتج. انتهاء الجلسة أو إغلاق المتصفح قد يتطلب إعادة الربط وإعادة اختيار الملف.

### عرض الصور للزائر

عرض الصور هو نقطة الاختبار الحاسمة لأن الخطة المجانية لا توفر خادمًا يقرأ الملفات الخاصة نيابة عن الزائر. صور المنتجات والشعار والعروض المنشورة يجب أن تسمح بالقراءة لأي شخص معه الرابط، مع إبقاء مجلد المنيو نفسه والملفات التي لم تُنشر خاصة. نغير صلاحية الملفات المقصودة فقط ولا نشارك Drive كله.

نختبر قراءة ملف صورة عام من Drive API وإظهاره في بطاقة المنتج من متصفح غير مسجل، باستخدام مفتاح API مقيد بنطاق الموقع وبـDrive API إن دعمت التجربة ذلك. دعم API key للقوائم العامة موثق؛ اعتماد مسار عرض محتوى الصور تحديدًا مشروط باختبار فعلي، ولا يُعلن أنه جاهز قبل نجاحه. نحفظ الرابط الرسمي ومعرّف الملف وresourceKey عند الحاجة.

للفيديوهات والملفات: نستخدم رابط معاينة أو تنزيل رسمي من Drive، ونختبر تضمين المعاينة إن سمحت الخدمة. نحمّل الفيديو عند الطلب، ونستخدم صورة غلاف منفصلة، ولا نفترض أن Drive يوفر منصة بث فيديو غير محدودة.

- لا نستخدم رابط صفحة مشاركة Drive كما لو كان رابط صورة مضمونًا.
- لا نعتمد رابط thumbnail مؤقتًا كرابط دائم.
- الزائر يستطيع الوصول للملفات التي منحها صاحب الحساب مشاركة عامة فقط، ولا يحصل على access token الأدمن.
- إخفاء منتج من Firestore لا يلغي مشاركة ملفه في Drive تلقائيًا. إلغاء الإتاحة يحتاج تعديل صلاحيات Drive أثناء جلسة Google نشطة، مع مراعاة استخدام الملف في أكثر من منتج.
- يظهر بديل للصورة ورسالة مناسبة للإدارة عند حذف الملف من Drive أو سحب إذن الربط.
- Google Drive له حصص استخدام؛ الأداء عند الحمل المتوقع جزء من اختبار التكامل.
- إذا لم تنجح صور البطاقات ضمن هذا المسار، لا نعتبر رابط «فتح على Drive» وحده تحقيقًا كاملًا لطلب عرض المنتجات. نعرض نتيجة الاختبار ونراجع الحل قبل التوسع في الواجهات، دون إضافة خدمة مدفوعة أو تغيير التخزين من تلقاء أنفسنا.

## نموذج بيانات أولي

كل نسخة تخدم نشاطًا واحدًا، ومعرّف المحل ثابت في إعدادات المشروع. المسارات التالية تفصل بياناته العامة عن إدارة الحساب:

- shops/{shopId}: الهوية والإعدادات العامة وروابط التواصل ومعرّف الشعار.
- shops/{shopId}/categories/{categoryId}: الاسم والترتيب وحالة العرض.
- shops/{shopId}/products/{productId}: المحتوى والأسعار والوسائط وحالة النشر والتوفر والخصم.
- shops/{shopId}/offers/{offerId}: نوع العرض وعناصر الباقة أو تفاصيل العرض الخاص ومدته وحالة نشره.
- shops/{shopId}/media/{mediaId}: رابط Drive ومعرّف الملف ونوعه وحجمه ومراجع استخدامه.
- إعداد حساب الإدارة المسموح ومعرّف مجلد Drive منفصلان عن المحتوى الذي يقرأه الزوار.
- لا تُحفظ رموز OAuth في أي من هذه المسارات، ولا توجد بيانات طلبات في النطاق.

القراءة العامة تكون للمحتوى المنشور فقط. الكتابة تتطلب Auth ومعرّف الأدمن المسموح، مع التحقق من الحقول والأسعار وأنواع الروابط داخل Firestore Rules. لا يستطيع المستخدم أن يجعل نفسه أدمن بكتابة مستند عضوية. Firestore Rules لا تعمل كفلتر، لذلك يجب أن تتضمن الاستعلامات العامة شرط النشر. قواعد Firestore تحمي قاعدة البيانات؛ صلاحيات Drive تحمي الملفات بشكل مستقل.

لا نحمّل كتالوج السوبر ماركت كله عند فتح الصفحة. نستخدم صفحات محدودة وcursor pagination واستعلامًا بالقسم وحالة النشر. سياسة البحث ستُختبر بحسب حجم الكتالوج؛ Firestore لا يوفر بحثًا نصيًا شاملًا تلقائيًا، فلا نعد بنتائج على منتجات لم تُحمّل باستخدام فلتر محلي فقط.

## التقنية المقترحة

- React + TypeScript + Vite لواجهة مناسبة لاستضافة Firebase Hosting.
- Tailwind CSS وshadcn/ui لبناء المكونات والنماذج والتنقل.
- مكتبة حركة مناسبة بعد تثبيت التصميم، مع CSS للحركات البسيطة.
- Firebase Web SDK + Firestore + Authentication.
- Google Identity Services + Google Drive API من متصفح الأدمن.
- Firestore Security Rules للتحقق من الكتابة والوصول، وفهارس بحسب الاستعلامات الفعلية.

هذه اختيارات مبدئية؛ لا توجد ملفات تطبيق حاليًا في مجلد المشروع.

## خطة الحركات والتصميم

- شاشة البداية: ظهور الشعار وانتقال سريع للمحتوى؛ لا تُجبر المستخدم على انتظار طويل لأجل الحركة.
- المنتجات: ظهور متدرج للكروت عند الوصول إليها، وانتقال خفيف عند تغيير القسم أو الفلتر.
- التفاصيل: انتقال متسق إلى صفحة المنتج مع تكبير الصورة عند الطلب.
- الأزرار: استجابة واضحة للمس والضغط، وحركات صغيرة للحالة.
- العروض الخاصة: معالجة بصرية مميزة وصور كبيرة، مع حركة محدودة في المساحة الظاهرة.
- الإدارة: انتقالات عملية ورسائل تقدم ونجاح وخطأ أثناء الحفظ والرفع.
- دعم prefers-reduced-motion، ولوحة المفاتيح، والتركيز المرئي، والتباين المقروء، والتكبير.
- اختبار 375 و768 و1024 و1440 بكسل، وعدم تغطية المحتوى بالشريط السفلي.

## سيناريوهات قبول أساسية

1. الزائر لا يستطيع فتح وظائف الإدارة أو الكتابة في البيانات أو الوصول للأسرار.
2. الأدمن يضيف منتجًا بسعر قطعة فقط؛ لا تظهر خانة سعر كرتونة فارغة للزائر.
3. الأدمن يضيف كرتونة وسعرها؛ يظهر السعران بوضوح.
4. الخصم يحسب على الوحدة المحددة، ويظهر السعر الأصلي والجديد، ويدخل المنتج قسم العروض تلقائيًا.
5. انتهاء الخصم أو حذفه يعيد السعر الصحيح ويزيل المنتج من عروض الخصم.
6. الباقة تعرض عناصرها وكمياتها وسعرها النهائي، ولا تضاعف الخصومات دون قاعدة صريحة.
7. العرض الخاص يظهر بصورة وتفاصيل وشروط ومدة صحيحة، وتختفي المسودات عن الزوار.
8. تغيير شعار المحل يحدّث الرأس وشاشة البداية، ولا يتسبب فشل تحميله في تعليق الموقع.
9. تغيير رقم واتساب ورابط فيسبوك في الإدارة يغير الزرين لدى العميل.
10. صورة مرفوعة موجودة في Drive الخاص بصاحب المحل، وفي Firestore بياناتها ورابطها فقط، دون ملف صورة أو base64.
11. زائر غير مسجل يرى صورة البطاقة المنشورة دون الحاجة لحساب Google؛ الملفات التي ما زالت خاصة لا تصبح متاحة بسبب حفظ الرابط في Firestore.
12. ملف كبير يكتمل رغم انقطاع الشبكة ضمن الحدود المتفق عليها، ولا تظهر بياناته كأنه مكتمل قبل نجاح الرفع.
13. سحب إذن Google أو حذف صورة من Drive يظهر حالة مفهومة ومسار إعادة ربط أو استبدال.
14. إخفاء منتج أو عرض يمنع قراءته العامة من Firestore، والواجهة توضح أن إلغاء رابط Drive يحتاج إلغاء مشاركته منفصلًا، مع الحفاظ على الملفات المستخدمة في محتوى آخر.
15. الهاتف يعرض المحتوى دون تمرير أفقي، والحركات تحترم تفضيل تقليل الحركة، والأزرار لا تغطي الأسعار.
16. رابط Firebase Hosting العام يعرض الموقع وتعمل عليه إعدادات OAuth وروابط التواصل.
17. اللغتان تعملان مع تبديل اتجاه الصفحة؛ اسم ووصف المنتج والقسم والعرض يظهران باللغة المختارة مع بديل واضح للمحتوى الذي لم يُترجم.
18. العملة الافتراضية جنيه، وتبديل العملة يتطلب مراجعة الأسعار ولا يحول قيمها تلقائيًا.
19. المقاسات والألوان اختيارية وتعرض السعر والتوفر الصحيحين عند إدخالهما.
20. التنقل في عدد كبير من المنتجات يعمل على دفعات، ولا يوحي البحث بأنه شامل إن كان يفلتر صفحة محملة فقط.
21. لا توجد Functions أو Storage أو account billing ضمن إعداد النسخة المجانية.

## متطلبات خارج الكود قبل التشغيل الفعلي

- مشروع Firebase على Spark، وتفعيل Auth بالإيميل وكلمة المرور وFirestore وHosting، وتحديد UID الأدمن خارج صلاحيات الكتابة العامة.
- تفعيل Google Drive API وإعداد OAuth client من نوع Web application وauthorized JavaScript origins وconsent screen للمشروع.
- مفتاح API خاص بقراءة بيانات Drive العامة عند الحاجة؛ يقيد بالخدمة والنطاق، ولا يمنح صلاحية لملفات خاصة.
- موافقة صاحب حساب Google أثناء الربط.
- ضبط OAuth للإنتاج قبل الإطلاق وفق متطلبات Google. هذا التصميم لا يستخدم refresh token؛ انتهاء access token يعالج بزر إعادة ربط من الأدمن.
- تحديد أحجام الملفات وحجم الزيارات المتوقع، وإعدادات حصص الخدمة والتنبيهات المناسبة.
- المجانية محدودة بحصص Firebase ومساحة Drive وحصص API؛ التطبيق لا يفرض عدد منتجات ثابتًا لكن الخدمات ليست بلا حدود. في Spark قد تتوقف بعض الخدمات مؤقتًا عند تجاوز الحصة بدل تحويل المشروع تلقائيًا للفوترة.
- لا يوجد اختبار سحابي مكتمل للرفع أو عرض الصور أو نشر فعلي حاليًا؛ إعداد Google Drive وحساب الأدمن المحدد لم يُختبرا بعد.
